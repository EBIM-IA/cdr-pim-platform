# CLAUDE.md — cdr-pim-platform

Working guide for this repository. Read this before changing code.

## What this is

The PIM for Casa del Rulimán: a product-information system, independent of Dynamics AX,
for ~45,000 SKU. A **modular monolith** with **hexagonal architecture**, in a pnpm +
Turborepo monorepo.

The decisions are in `docs/adr/`. They are baseline — do not change one without writing a
new ADR that supersedes it.

## The dependency rule

```
EXTERNAL SYSTEM  →  ADAPTER  →  PORT  →  APPLICATION  →  DOMAIN
```

Inwards, always. Concretely:

| Layer             | May import                                  | Never                                                            |
| ----------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| `domain/`         | `@cdr/shared` primitives, other domain code | Any framework, driver or SDK; any outer layer                    |
| `application/`    | domain, ports, `@nestjs/common` (DI only)   | Drizzle, `postgres`, `openai`, `@aws-sdk`, adapters, controllers |
| `infrastructure/` | anything                                    | —                                                                |
| `presentation/`   | application, domain, `@cdr/contracts`       | adapters directly                                                |

**These are enforced, not suggested.** `apps/api/test/architecture/boundaries.spec.ts` scans
every file and fails the build with the offending import named. If it fails, introduce a
port — do not relax the rule. Treat a change to that spec as an architectural change.

## Repository map

```
apps/web      Next.js 15 · React 19 · Tailwind v4 · shadcn/ui
apps/api      NestJS 11 · Drizzle · PostgreSQL + pgvector
apps/worker   Node 24 · SQS consumer

packages/contracts   Zod schemas shared by all three (HTTP DTOs + job envelope)
packages/shared      Result, DomainError, JSON logger, UUID, Clock, correlation context
packages/config      validated environment schemas per app
packages/messaging    QueuePort + SqsQueueAdapter + InMemoryQueueAdapter
packages/storage      ObjectStoragePort + S3StorageAdapter + InMemoryStorageAdapter
```

Bounded contexts in `apps/api/src/modules/`: catalog, categories, attributes, equivalences,
search, ai, imports, integrations, ax-integration (temporary QAS mock), identity, audit, health. Their real status is in
`docs/architecture/MODULE_ARCHITECTURE.md` — several are scaffolding on purpose.

## Commands

```bash
pnpm dev                 # all three apps

pnpm test:integration    # needs: docker compose up -d postgres
pnpm lint  pnpm typecheck  pnpm build

pnpm db:new <name>       # scaffold the next migration

pnpm --filter @cdr/api <script>
```

## How to add things

### A use case

1. `application/<verb>-<noun>.use-case.ts`, `@Injectable`, one public `execute`.
2. Depend on **ports** via `@Inject(TOKEN)`. Never on an adapter.
3. Register it in the module's `providers`.
4. Unit-test it with a fake implementing the port — no database.

### An adapter

1. `infrastructure/<area>/<name>.adapter.ts`, implementing an existing port.
2. Translate vendor errors into `DomainError` subclasses (`DependencyUnavailableError`).
   A vendor exception must never escape this file.
3. Bind it in the module: `{ provide: PORT_TOKEN, useClass: TheAdapter }`.
4. Integration-test it if it talks to PostgreSQL.

### A port

1. `domain/ports/<capability>.port.ts` — an interface plus its `Symbol` token.
2. Name the **capability**, not the vendor: `ProductVectorIndexPort`, not `PgVectorRepo`.
3. Keep it narrow. Add methods when a use case needs them, never speculatively.

### A migration

```bash
pnpm db:new add_product_attributes
# write the SQL, with a comment explaining WHY and the reverse where sensible
pnpm db:migrate
```

Then update the matching `*.tables.ts` so `schema-drift.spec.ts` passes.

**Applied migrations are immutable.** The runner verifies a SHA-256 of every applied file
and refuses to run if one changed — that is what keeps QAS and PRD from diverging. To change
something, write a new migration.

### A job

1. Add the type to `JobType` in `packages/contracts` with a payload schema.
2. Implement `JobHandler` in `apps/worker/src/handlers/`.
3. Register it in `HandlerRegistry` in `apps/worker/src/main.ts`.
4. **The handler must be idempotent** — SQS delivers at least once.
5. Throw `PermanentJobError` for anything a retry cannot fix.

## Standards

- All instants **UTC** internally; localise only at the presentation edge.
- **UUID v4** for identifiers, generated by the application.
- `snake_case` in the database, `camelCase` in TypeScript.
- API paths under `/api/v1`.
- Errors use the shared envelope: `code`, `message`, `details`, `correlationId`,
  `timestamp`, `path`.
- Validate at the boundary with the schema from `@cdr/contracts` — the same schema the web
  client uses.
- TypeScript strict. `any` is a lint error; justify any exception in a comment.

## Prohibited

- ❌ `any` without a written justification
- ❌ Frameworks, drivers or vendor SDKs in `domain/`
- ❌ Cross-module database access — go through the other module's published port
- ❌ Business logic in controllers or adapters
- ❌ `process.env` outside `shared/config/config.module.ts` and the standalone CLIs
- ❌ Editing an applied migration
- ❌ Hardcoded model names, URLs, buckets or queue names — they are configuration
- ❌ Secrets in git, including in tests
- ❌ Redis, Kubernetes, Kafka, RabbitMQ, Elasticsearch — see the ADRs
- ❌ Logging a password, token, API key or secret
- ❌ Global `schema.sync()` or any auto-migration in production

## Workflow

```
feature/<short-description>  →  pull request  →  green CI  →  squash-merge to main
```

`main` is protected and always deployable. Environments are stages of promotion, not
branches. Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `ci:`).

Before pushing: `pnpm verify`.

## When to stop and ask

Stop and report rather than inventing:

- AWS credentials, OpenAI keys, or any real endpoint or schema for Dynamics AX
- A functional rule that has not been decided (taxonomy, mandatory attributes, equivalence
  rules, publication criteria, data-quality thresholds)
- Anything that widens the agreed scope, or contradicts an ADR

A stub that fails loudly with a documented reason beats a plausible guess. That is why
`AxProductSourceAdapter` throws instead of returning empty results.
